# T005 — валидация и единственная проверка на отложенном периоде

## Контекст

Прочитай `CLAUDE.md`, `docs/DECISIONS.md` (ADR-015, ADR-016), `docs/reports/T004-dev.md`, `docs/reports/T004b-dev.md`. T004b смержен.

Критерии выбора и прохождения уже зафиксированы в ADR-016 до любых прогонов на `val` и `holdout`. Эта задача их исполняет и ничего в них не меняет. Если при работе обнаружится, что критерий нельзя вычислить так, как он записан, — остановиться и описать проблему в отчёте, а не трактовать его по-новому.

## Git

Ветка `task/005-validation`, PR в `main`. Готово, когда CI зелёный на Ubuntu и Windows.

## 0. Первый коммит — что будет после T005

До любых прогонов дописать в `docs/DECISIONS.md` решение о действиях по итогам T005. Его цель — заранее исключить объяснение результата задним числом.

**Если отложенный период пройден.** Это разрешение перейти к T006 (Demo) с малым риском, а не доказательство преимущества. Отложенный период длится около года. Стандартная ошибка Sharpe за год около 1, поэтому условие «Sharpe > 0» стратегия без преимущества выполняет примерно в половине случаев. Уровень риска для Demo и live выбирается в T006 только по данным `dev` и `val`, отложенный период для этого не используется.

**Если не пройден.** Семейство пробойной трендовой корзины не переходит к исполнению. Параметры не меняются, окно не продлевается, повторных попыток нет. Следующее направление — T007 (funding carry): это другой источник дохода, премия за риск, а не прогноз направления.

**Если на `val` нет допустимого кандидата.** Отложенный период не запускается, действует ветка «не пройден».

## 1. Прогоны на `val`

Все семь кандидатов в режиме `exact`, капитал $10 000, конфигурации из T004b без изменений, кроме `period = "val"`:

```
V1x, V2x, V3x, V4x, H1, H2, H3
```

Плюс эталоны на `val` в режиме `exact`: `buy_and_hold_btc` и `equal_weight_universe`.

Запуск каждого кандидата — с `--allow-val`. Все запуски попадают в `reports/period-access-log.jsonl`.

## 2. Выбор кандидата

Точно по ADR-016:

1. Отбросить кандидатов, у которых меньше 100 закрытых позиций на `val`, максимальная просадка хуже −20% или Sharpe не определён.
2. Из оставшихся выбрать наибольший Sharpe; при точном равенстве — по ID.
3. Если никого не осталось — отложенный период не запускается.

Выбор делается скриптом, а не вручную. Скрипт `tb research select --period val --candidates ...` читает `metrics.json` прогонов, применяет правило и пишет результат в `docs/reports/T005-selection.json`: все кандидаты, их метрики, причины исключения, выбранный ID. Выбор коммитится **до** запуска отложенного периода.

## 3. Единственный прогон на `holdout`

Только выбранный кандидат, режим `exact`, $10 000, `--allow-holdout` с подтверждением в консоли. Плюс эталон `buy_and_hold_btc` в режиме `exact` на том же окне.

Остальные кандидаты на `holdout` не запускаются — ни для сравнения, ни «для информации». Иначе появится соблазн заменить выбор.

Прохождение, точно по ADR-016, требует одновременно:

- Sharpe > 0;
- максимальная просадка не хуже −25%;
- доходность кандидата выше, чем доходность эталона BTC, умноженная на отношение годовой волатильности кандидата к волатильности BTC на том же окне.

Если волатильность BTC нулевая или не определена, критерий не считается пройденным.

Проверку выполняет скрипт `tb research holdout-verdict`. Результат записывается в `docs/reports/T005-holdout.json`.

## 4. Прогон на $1000 в режиме `exchange` — только если отложенный период пройден

Тот же кандидат на `val` в режиме `exchange` с капиталом $1000. Отложенный период здесь **не** используется. Цель — понять, насколько реализуема стратегия на реальном маленьком счёте:

- число пропусков по минимальному размеру;
- средний размер позиции;
- разница с `exact`.

Результат пойдёт в T006.

## 5. Отчёт `docs/reports/T005.md`

1. Таблица всех семи кандидатов на `val`: доходность, CAGR, волатильность, Sharpe и его стандартная ошибка, максимальная просадка, закрытые позиции, средняя экспозиция, причина исключения.
2. Эталоны на `val`.
3. Выбранный кандидат и шаги правила выбора.
4. Для выбранного кандидата: сравнение `dev` и `val` — метрики и разбивка по годам.
5. Результат на `holdout`: метрики кандидата и эталона BTC, расчёт каждого из трёх условий с числами, итоговый вердикт.
6. Если пройден — раздел про $1000 из пункта 4.
7. Содержимое `reports/period-access-log.jsonl`: какие запуски были на `val` и `holdout`.
8. Итоговое решение по ветке из пункта 0, без новых интерпретаций.

## Тесты

- `tb research select`:
  - исключение по каждому из трёх условий;
  - выбор максимума;
  - равенство решается по ID;
  - пустой список допустимых → отложенный период запрещён.
- `tb research holdout-verdict`:
  - каждое условие по отдельности приводит к провалу;
  - все три выполнены → проход;
  - нулевая волатильность BTC → провал.
- Попытка запустить на `holdout` второй раз с другим кандидатом, если в журнале уже есть запуск стратегии на `holdout`, требует отдельного флага `--override-holdout-lock` и пишет предупреждение в журнал. В этой задаче флаг не используется.

## Вне рамок задачи

Изменение кандидатов, параметров, критериев, периодов. Комбинации гипотез. Выбор уровня риска для live (T006). Исполнение.

## Критерии готовности

1. Все проверки из `CLAUDE.md` зелёные; CI зелёный на обеих ОС.
2. Коммит с решением из пункта 0 сделан до любых прогонов.
3. Коммит с `T005-selection.json` сделан до прогона на `holdout`.
4. В журнале доступа ровно один запуск стратегии на `holdout`.
5. Отчёт оформлен по разделу 5, вердикт вычислен скриптом.
