# T006a2 — непрерывность прогона: простой, обрывы сети, перезапуски

## Контекст

Прочитай `CLAUDE.md`, `docs/DECISIONS.md` (ADR-018 и новее), `docs/reports/T006a.md`. T006a смержен вместе с доработками:

- трактовка пустого `liqPrice`;
- выделенный капитал стратегии;
- защитные закрытия не меняют состояние стратегии.

Выделенный капитал для Demo — **$1000**, как планируемый live.

Бот работает на домашнем Windows-компьютере. Пропадание света, сети, сон компьютера и перезапуски неизбежны. Задача — чтобы один Demo-прогон оставался одним прогоном при любых перерывах:

- после перезапуска бот узнаёт свой прогон;
- восстанавливает всё, что произошло на бирже, пока он был выключен;
- продолжает учёт без дыр.

Новый прогон начинается только явной командой.

Позиции во время простоя защищены биржевыми стопами. Бот без связи теряет только обновление трейлинг-стопа (он остаётся на прежнем уровне, то есть не ослабляется) и своевременность новых решений.

## Git

Ветка `task/006a2-run-continuity`, PR в `main`. Готово, когда CI зелёный на Ubuntu и Windows.

## 0. Первый коммит — правило для T006b

Записать в `docs/DECISIONS.md` до реализации:

- **Не сбрасывает отсчёт** 14 дней T006b: перезапуск после внешнего сбоя (свет, сеть, сон, перезагрузка), если `tb run verify` после него проходит и ручных торговых действий не было. Суммарный простой и число перезапусков указываются в отчёте T006b.
- **Сбрасывает отсчёт:**
  - ручная сделка или ручное изменение стопа на счёте;
  - изменение конфигурации прогона;
  - невосстановимый разрыв учёта (пункт 5).

## 1. Идентичность прогона

`tb run start --name demo-001` создаёт каталог `data/live/demo/runs/<run_id>/` и `manifest.json`:

- `run_id`, время создания через `Clock`, git commit;
- хеш конфигурации прогона: параметры стратегии, риск, лимиты, выделенный капитал, режим количества, плечо;
- обезличенный хеш идентификатора счёта;
- статус `active`.

Файл-указатель `active_run` в `data/live/demo/`.

**Поведение команд:**

- `tb run --loop` и `tb run --once` без аргументов продолжают активный прогон.
- Если активного прогона нет, они отказываются стартовать и подсказывают `tb run start`.
- Если хеш текущей конфигурации отличается от хеша в манифесте, бот отказывается продолжать. Сменить конфигурацию можно только через `tb run close`, который записывает итоговое состояние, и `tb run start` нового прогона.
- Смена версии кода внутри прогона допускается и пишется событием `code_version_change`. Если изменились модули `strategies/`, `portfolio/` или `execution/`, нужен флаг `--allow-code-change`, и событие помечается как существенное.

## 2. Надёжность журнала

Все журналы прогона — дописываемые строки JSON.

**Каждая запись содержит:**

- порядковый номер `seq`;
- время;
- тип;
- `prev_hash` — SHA-256 предыдущей записи;
- `hash` — SHA-256 собственного содержимого вместе с `prev_hash`.

**Запись:** строка, затем `flush`, затем `fsync`.

**Проверка при старте:**

| Ситуация | Действие |
|---|---|
| Последняя строка неполная или не разбирается (свет пропал во время записи) | Сохранить её в `*.corrupt-<время>`, обрезать файл до последней целой записи, записать событие `journal_tail_repaired` |
| Разрыв цепочки хешей или пропуск `seq` в середине файла | Аварийная остановка, нужна ручная проверка |

**Снимок состояния** — стратегия, позиции бота, кривая капитала. Пишется после каждого цикла атомарно: временный файл, `fsync`, `os.replace`. В снимке записан `seq` последней учтённой записи журнала.

## 3. Состояние стратегии

При старте состояние восстанавливается из снимка и **независимо пересчитывается** по истории свечей и событиям стопов этого прогона. Если результаты не совпадают — аварийная остановка с описанием расхождения.

## 4. Обнаружение простоя

**Сердцебиение.** Файл `heartbeat` атомарно обновляется раз в минуту: время по часам и монотонный счётчик процесса.

**Обнаружение:**

- При старте простой = текущее время − последнее сердцебиение. Если больше 2 минут, записывается событие `downtime` с интервалом.
- Во время работы цикл сравнивает прирост системного и монотонного времени. Скачок больше 2 минут означает сон или гибернацию и обрабатывается как простой.

## 5. Восстановление событий биржи за время простоя

За интервал от `последний снимок − 5 минут` до текущего момента, со всей пагинацией, запрашиваются:

- исполнения;
- история заявок;
- закрытый PnL;
- журнал транзакций (фандинг, комиссии).

**Дедупликация** — по идентификаторам биржи: `execId`, `orderId`, идентификатор транзакции. Повторное восстановление не создаёт дублей. Восстановленные записи помечаются `recovered = true`.

**Срабатывание биржевого стопа** во время простоя — это стоп стратегии, как в бэктесте. Состояние стратегии обновляется по её правилам. Защитные закрытия исполнителя (T006a, пункт 3) так не трактуются.

**Лимиты истории биржи.** Перед реализацией сверь с документацией Bybit, за какой срок и какими окнами доступна история исполнений и транзакций. В T006a обнаружено ограничение около 7 дней. Если простой превышает то, что можно восстановить полностью:

- записывается `unrecoverable_gap`;
- новые торговые действия блокируются;
- биржевые стопы не трогаются;
- продолжение возможно только через `tb run verify --accept-gap` после ручной проверки;
- в T006b такой разрыв сбрасывает отсчёт.

**Кривая капитала.** Пропущенные дневные точки на 00:00 UTC восстанавливаются по восстановленным исполнениям и фандингу и по дневным ценам закрытия из публичного API. Помечаются `reconstructed = true`.

## 6. Пропущенные решения

- Если пропущено несколько дневных решений, выполняется только последнее: цели зависят от состояния рынка, а не от истории решений. Оно помечается `late = true` с величиной опоздания.
- Если за время простоя была плановая пересборка вселенной, сначала пересобирается вселенная.
- Трейлинг-стопы обновляются до значения, которое стратегия вычисляет на последней закрытой свече. Они никогда не ослабляются.

## 7. Обрывы сети во время работы

Цикл не завершается из-за сетевых ошибок. Повторы идут с экспоненциальной паузой и джиттером, максимум паузы — 5 минут.

Если решение дня не удаётся выполнить из-за сети:

- попытки продолжаются;
- с первого часа — уведомление раз в час, если Telegram доступен;
- когда сеть вернулась — выполнение с пометкой `late = true`.

Если решение не выполнено до следующего дневного решения, выполняется только новое (пункт 6).

## 8. Автозапуск на Windows

`tb service install-windows` создаёт задачу Планировщика Windows (через `schtasks`), которая:

- запускает `uv run tb run --loop` в каталоге проекта при входе пользователя в систему;
- перезапускает процесс при сбое;
- пишет вывод в `data/live/demo/logs/`.

`tb service uninstall-windows` удаляет задачу. Перед созданием команда печатает, что именно будет сделано, и просит подтверждение.

Отдельный раздел в README, раздел «Работа на домашнем компьютере»:

- отключить сон при питании от сети;
- при желании включить в BIOS автоматическое включение после восстановления питания;
- по желанию — ИБП.

Для Linux автозапуск через systemd будет в T009.

## 9. Уведомления о перезапуске

После любого перезапуска с простоем — сообщение в Telegram:

- длительность простоя;
- что восстановлено: исполнения, стопы, фандинг;
- результат сверки;
- было ли запоздавшее решение;
- статус прогона.

Ежедневная сводка дополняется строкой: суммарный простой и число перезапусков за прогон.

## 10. `tb run verify`

Проверяет:

- цепочки хешей всех журналов;
- непрерывность `seq`;
- совпадение кривой стратегии, пересчитанной из журнала, с данными биржи (исполнения, фандинг, позиции);
- состояние стратегии против независимого пересчёта.

Выводит список простоев, восстановлений и разрывов. Код выхода 0 — всё согласовано, 1 — есть расхождения.

## Тесты (без сети)

- Неполная последняя строка → обрезка и событие.
- Разрыв цепочки в середине → остановка.
- Атомарный снимок переживает прерывание между записью временного файла и заменой.
- Продолжение активного прогона после «перезапуска» процесса в тесте. Отказ при изменённом хеше конфигурации. Событие смены кода и флаг.
- Восстановление:
  - исполнения и фандинг за простой без дублей при повторном запуске;
  - стоп, сработавший во время простоя, учтён один раз и обновил состояние стратегии;
  - защитное закрытие состояние не меняет.
- Пропущено 3 дня → выполнено одно решение с `late = true`. Пересборка вселенной внутри простоя.
- Скачок часов при монотонном времени → простой.
- Сеть недоступна дольше окна решения → цикл не падает, решение выполняется после восстановления.
- Простой длиннее доступной истории → `unrecoverable_gap` и блокировка.
- `verify`: согласованный прогон → 0; подменённая запись → 1.
- `install-windows` формирует ожидаемые аргументы `schtasks` (без реального выполнения в тестах).

## Проверка на Demo (владелец)

Прогон с выделенным капиталом $1000 и хотя бы одной открытой позицией.

1. **Внезапная остановка процесса.** Закрыть окно или завершить процесс в Диспетчере задач, подождать 10 минут, запустить снова. Проверить сообщение о простое и `tb run verify`.
2. **Потеря сети.** Отключить сетевой адаптер на 10 минут при работающем боте. Бот не падает, после восстановления сверка чистая.
3. **Пропуск решения.** Остановить бота до 00:00 UTC, запустить после 00:10 UTC. Одно запоздавшее решение, стопы обновлены.
4. **Автозапуск.** Перезагрузить компьютер, бот стартовал сам и продолжил тот же прогон.
