# T001a — проверка Bybit на Windows и реальные фикстуры

Проверено 2026-09-29 по Москве (2026-09-28 UTC), Windows, Python 3.12.13.
База: `main` после мержа T001 (`239f3b2`); ветка `task/001a-bybit-live-validation`.
Публичный API: `https://api.bybit.com`, настройки проекта по умолчанию, без ключей.

## Что сделано

- Исправлен путь истории фандинга на `/v5/market/funding/history` в клиенте и тестах.
- При первом реальном запуске обнаружена преждевременная остановка пагинации свечей:
  из полной страницы в 1000 строк удалялась незакрытая свеча, и 999 оставшихся строк
  ошибочно считались последней страницей. Первый запуск сохранял только историю
  с 2024-01-03, а повторный добавлял ещё 1097/1024/810 строк вместо ожидаемого нуля.
- Условие продолжения и граница следующей страницы теперь определяются по исходным
  строкам ответа. Добавлены тесты полной страницы с незакрытой свечой, страницы
  только с незакрытой свечой и пустого ответа. Отдельный регрессионный тест
  использует полную страницу из 1000 строк (999 закрытых + 1 незакрытая),
  следующую страницу и проверяет все 1002 ожидаемые закрытые свечи без пропусков
  и дублей, включая точную границу `end = oldest_raw_timestamp - 1`.
  Проверяются параметры запросов,
  стыки страниц фандинга и передача непрозрачного курсора инструментов.
- Пересняты 11 JSON-фикстур: время сервера, свечи 1d/4h с пагинацией,
  фандинг, инструменты и ошибка `10001`. Происхождение, параметры запросов,
  правила обрезки и ссылки на документацию указаны в
  [README фикстур](../../tests/fixtures/bybit/README.md).
- Все шесть команд T001 повторно выполнены на чистом кэше после исправления.
  Повторная синхронизация дала `+0 rows` по всем трём символам; SHA-256 файлов совпал.

## Что сознательно не сделано

- `rate_limit_10006.json` сохранён как явно обозначенная синтетическая фикстура.
  При нормальной частоте запросов такой ответ не поступал; нагрузку для его
  получения специально не создавали.
- Исправления отправлены в [PR #3](https://github.com/branch-danya-dev/trending-basket/pull/3).
  CI на Ubuntu/Windows прошёл на `fd180a7`; после добавления теста на 1000 строк
  он повторно проверяется перед merge.

## Допущения и фактические границы данных

Начальная дата в запросе — 2021-01-01. Bybit вернул свечи BTCUSDT с этой даты,
ETHUSDT с 2021-03-15, SOLUSDT с 2021-10-15. Последняя закрытая дневная свеча —
2026-09-27. Отсутствующие данные до первой доступной свечи не создавались;
`check` проверяет пропуски внутри сохранённого диапазона.

Дополнительная сверка 2026-09-28 в 22:42:45 UTC: время получено через
`/v5/market/time`, `launchTime` — через `/v5/market/instruments-info`.
Каждый timestamp в кэше сравнен с полным ожидаемым дневным диапазоном.

| Символ | `launchTime`, UTC | Начало диапазона с учётом `--since` | Ожидалось / получено |
|---|---|---|---|
| BTCUSDT | 2020-03-15 | 2021-01-01 | 2096 / 2096 |
| ETHUSDT | 2021-03-15 | 2021-03-15 | 2023 / 2023 |
| SOLUSDT | 2021-10-15 | 2021-10-15 | 1809 / 1809 |

Свеча за 28 сентября закрывается только 29 сентября в 00:00 UTC
(03:00 по Москве). После этого ожидаемые количества увеличатся на одну строку:
2097 / 2024 / 1810. Ожидание 2097 свечей ETHUSDT с 2021-01-01 не соответствует
`launchTime` этого инструмента в текущем ответе API.

История фандинга BTCUSDT/ETHUSDT начинается с 2021-01-01, SOLUSDT —
с 2021-06-29 08:00 UTC; последнее наблюдение — 2026-09-28 16:00 UTC.
Фандинг и свечи могут иметь разные доступные начальные даты.

Снимок содержит 886 инструментов категории `linear`, как вернул API.
Поля `minNotionalValue` и `fundingInterval` разобраны успешно. Запрос фандинга
только со `startTime` реально вернул `retCode=10001`; рабочий клиент передаёт
и `startTime`, и `endTime`.
